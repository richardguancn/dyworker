# DYWorker 性能优化方案

日期：2026-10-15。范围：当前工作区代码与用户提供的系统监控截图。

本次交付是优化方案及检查依据，尚未实施产品性能改动。检查期间记录的源码版本为 `main` 分支的 `c9bcf27`；开始检查时工作区已有注释定位改动，结束时该改动已由其他工作提交为 `6ef3b74`，本次未修改产品代码。截图中安装版本、操作系统版本、硬件和当时任务状态未知，不能认定截图运行的就是当前代码。

## 1. 要解决的问题与完成标准

目标：让应用闲置时少占资源，长对话持续输出时仍能顺畅输入、滚动和切换，任务结束后资源占用能够回落，同时保持消息、保存、审批、停止和定时任务行为正确。

本方案的完成标准：核对现状；实际运行已有检查；区分证据和推测；列出实施顺序、验收办法与回退条件。后续优化工程的完成标准：同一台目标 Linux 电脑上，优化前后使用相同数据和操作比较，达到下面约定的指标，并通过功能检查。不能用本机模拟检查代替目标电脑验收。

截图中 DYWorker 显示：CPU 119.6%，内存 927.5 MB，磁盘读写 1756 KB/s，网络 49.4 KB/s。这只能证明截图时刻的占用；磁盘栏没有区分读和写。CPU 的统计口径、是否合并子进程未知，不能解读为“整台电脑超过 100%”；内存单次读数也不能证明泄漏。系统监视器自身显示 CPU 83.6%，采样工具的干扰也应在复测时核实。

优先顺序：**先测清持续负载来自哪里，再消除高频重复工作，最后处理长历史记录和后台资源的规模问题。** 若采样表明主要负载来自本地模型、网页或外部工具，就先处理相应部分，不能仅因界面代码复杂而认定它是截图问题的主因。

## 2. 本次已验证的依据

### 当前代码事实

| 检查项 | 当前情况 | 对方案的影响 |
| --- | --- | --- |
| 主界面状态 | 现有静态检查统计到 `App` 直接持有 153 个 `useState`、84 个 `useEffect` | 是高频更新影响范围较大的线索，数量本身不是耗时证据 |
| 对话展示 | 当前会话仍遍历全部消息；轮次摘要逐轮查找后续消息，展示中再次查找轮次 | 优先验证重复遍历和历史消息更新成本 |
| 拖动面板 | 移动事件直接更新主界面宽度状态，监听也依赖宽度 | 可将拖动中的尺寸更新局部化 |
| 流式文字传输 | `executeAgentRun` 已按 50 ms 合并正文、思考快照；其他事件会先冲刷缓冲 | 保留顺序保障；不能假定所有入口均受同一限制，也不是全局严格每秒 20 个事件 |
| 正文展示 | 已完成消息已复用渲染结果，输出中的正文已有分块处理 | 不重新实施已有优化；继续测量收尾和长单块内容 |
| 会话保存 | 已按会话分文件、只传变化会话；运行时 30 秒兜底保存，空闲变化后 180 ms 防抖 | 不能再把问题描述成“每个字重写全部会话” |
| 会话内存 | 存档模块有 `loadAll()` 与 `byId` 完整对象缓存 | 核查全量读取的调用路径、对象副本和缓存释放策略 |
| 任务过程记录 | 请求和回复会转成完整文本；一次运行的记录先在内存积累；显示缓存按条数限制 | 需要按字节量、生命周期检查；条数上限不能约束单条大内容 |
| 内置网页 | 非当前网页仍创建对应网页视图 | 隐藏不等于已释放；先测后台网页占用和任务依赖 |
| 本地能力 | 本地审核模型已有 5 分钟闲置卸载，语音识别已有 3 分钟闲置停止逻辑 | 先验证释放是否生效，不把它们写成尚未实现 |
| 注释与搜索 | 注释定位会查找正文并量位置；打开搜索时，搜索计算依赖会话变化 | 在带注释、打开搜索的长对话中单独测，不能用普通对话数据覆盖结论 |

代码定位：

- `src/App.tsx`：`updateSession`、`conversationTurnPreview`、`conversationTurns`、`buildSessionSavePayload`、面板拖动、`updateAnnotationMarkers`、搜索高亮、网页视图。
- `src/InteractiveMessage.tsx`：`MarkdownChunk`、`StreamingMessage`、`InteractiveMessage`。
- `electron/main.mts`：`executeAgentRun` 的流式合并与 `runTrace`。
- `electron/session-archive.mts`：`loadAll`、`applyDelta`、`writeSessionFile`、`contentFingerprint`。
- `electron/host/dsh-runtime/trace.mts`：请求、回复和工具结果记录。
- `electron/local-reviewer.mts`、`electron/local-asr-server.mts`：闲置释放。

旧的 `performance-audit-App.md` 已注明属于历史审计。本方案不沿用它的旧行号和未重新证实的结论。尤其是：文字清理缓存清空会造成重新清理，但同值字符串不会自动让已完成消息重新解析；不能宣称每 20 秒一定出现全量正文重解析。

### 本机模拟检查

环境：macOS、arm64、Node v22.21.1；真实界面组件加模拟会话，不连接在线模型。基准程序关闭图形加速，页面使用 macOS 分支，不能代表 Linux 图形驱动或正式安装包。

已运行静态检查、基准页构建，以及 120 条、600 条历史消息的 `all` 场景。受限环境第一次启动 Electron 退出；扩大运行权限后两组检查完成，结果中的 `errors` 均为空。控制台另有基准页安全策略、公式文本和接口弃用提示，不应称为完全无警告。

| 单次检查指标 | 120 条消息 | 600 条消息 |
| --- | ---: | ---: |
| 初始页面元素数 | 9,347 | 45,829 |
| 主动触发界面更新的单次处理耗时，第 95 百分位 | 3.4 ms | 15.3 ms |
| 模拟文字事件更新的单次处理耗时，第 95 百分位 | 3.9 ms | 19.0 ms |
| 模拟文字事件期间的计时延迟，第 95 百分位 | 2.4 ms | 49.1 ms |
| 该场景观测到的超过 50 ms 的长任务 | 0 次 | 1 次，85 ms |

解释：这里的“第 95 百分位”表示约 95% 的采样不超过该值。上述处理耗时来自 React 的渲染计时，不是完整屏幕绘制耗时；计时延迟也不是鼠标响应实测。`idle` 子场景会主动触发窗口状态变化，**不是静置 CPU 测试**。`all` 的文字事件没有完整启动真正的输出状态。两组各运行一次，只说明值得进一步调查的规模趋势，不作统计显著性或收益承诺。

另外运行了 120 条历史消息、16,000 字符、每次增加 40 字符的 `longstream` 场景：完成，`errors=[]`，但 `streamMarkup=null`。工具的 `streamingPath=true` 来自传入参数，不是页面状态断言，不能据此认定真正的持续输出显示路径已通过检查。因此不把这组耗时用作该路径的合格基线。第一步须同步更新模拟事件与页面断言，覆盖桌面、渠道、定时和唤醒入口；确认输出中的正文实际存在，再测长回复。原始结构化结果见同目录的 `performance-baseline-2026-10-15.json`。

## 3. 第一步：在问题电脑上建立可比较的记录

建议先用半天至一天完成，时间是工作量预估，取决于能否复现。

1. 记录安装版本、系统版本、CPU、内存、图形驱动、会话数量、网页数量、使用的模型，以及截图对应任务。采用正式安装包，同一次比较保持设置和数据一致。
2. 每秒记录应用各进程的 CPU、内存、磁盘读写增量，覆盖主进程、主界面、网页、图形处理、插件与工具子进程。先建立进程对应关系，避免漏算工具或重复计数。Linux 同时报告 PSS（按比例分摊共享内存）与 RSS（驻留内存）；不可把多进程 RSS 总和直接当成独占物理内存。
3. 同步记录任务状态、文字事件数量及大小、保存次数及字节数、过程记录大小、界面长任务。默认不收集正文、密钥和截图；性能记录限制大小、测完停止，避免测量本身持续写盘。
4. 每个场景预热 1 分钟、记录 5 分钟、重复 3 次；记录后台干扰和是否使用详细分析工具。对比时先用轻量采样，再在热点出现时短时录制详细调用记录。
5. 连续运行检查另做 30 分钟，并重复打开、关闭网页及切换会话 20 次；比较每次回到相同状态后的占用，判断是缓存平台期还是持续积累。

场景至少包括：空会话静置；长会话静置；120/600/2000 条历史消息下输出同一份固定内容；长代码块与表格；输入、滚动和拖宽度；搜索与注释；3 个后台任务；网页关闭/单页/多页；本地审核和语音使用前后；任务停止与完成后。

复现先用固定事件回放隔离界面成本，再补真实模型和真实工具任务。模型等待时间与本地响应时间分开记录。

## 4. 第二步：优先消除高频重复工作

建议拆成可独立验证的小批次，每批保留前后对照数据；首批预计 2—3 个工作日。

| 优先事项 | 具体措施 | 如何确认有效 | 主要约束 |
| --- | --- | --- | --- |
| 长对话反复扫描 | 一次建立消息与轮次对应关系；只更新正在变化的轮次；需要时再生成悬停详情 | 120/600/2000 条消息下记录计算耗时与调用次数 | 正在输出的详情不能长期停留在旧内容 |
| 拖动牵动整个界面 | 拖动时按画面刷新节奏局部更新宽度，松手后再保存最终尺寸；稳定事件监听 | 连续拖动时检查主界面更新次数、输入响应和布局 | 保持最小宽度、窗口缩放、折叠和重启恢复正确 |
| 缓存周期性全部清空 | 为文字清理缓存设置条数和字节预算；逐项淘汰；持续变化正文避免积累大量旧快照 | 比较命中率、清理时间与缓存字节量 | 只按测量收益决定是否保留，不宣称必然消除卡顿 |
| 隐藏面板仍计算 | 过程面板关闭时继续保存必要数据，停止生成展示内容；展开后再加载 | 面板开关前后比较处理时间与内存 | 不得丢失错误、审批、执行记录和完成状态 |
| 搜索与注释定位 | 只对受影响内容更新；合并同一帧测量；位置未变不重复更新状态 | 开搜索和带注释时重复长回复、滚动与切换 | 保留精确引用定位，不能恢复已失效的位置缓存 |
| 保存与记录成本 | 测量后复用同一次序列化结果；合并重复保存；过程记录采用有大小限制的缓冲和分批写入 | 分开报告读写字节、保存耗时、缓冲大小和结束时的停顿 | 不扩大现有 30 秒兜底窗口；保存成功后才确认已保存，失败必须可重试 |

不统一粗暴降低所有消息刷新频率。现有 50 ms 合并先保留；若传输占比仍高，再评估“增量内容＋定期完整快照”。必须支持顺序校验、重复事件、丢失后恢复、切换会话和结束前冲刷；审批、错误、停止及完成事件不等待低频刷新。

## 5. 第三步：缩小更新范围和内存常驻量

预计 3—5 个工作日，按第一步证据调整顺序。

- 将会话列表、消息列表、输入框、工具面板划分为独立更新区域。新文字只更新对应消息与必要状态；历史消息没有变化时复用原结果。先稳定传给消息行的数据和动作，再验证隔离确实生效。只拆文件不算完成。
- 为大历史会话建立轻量目录，按需读取正文。主进程缓存和界面缓存都设字节预算，优先释放已保存、非当前、非运行中的会话。检查历史检索、渠道消息、定时唤醒等所有读取者，避免一次 `loadAll()` 又把全部历史载入。
- 当前 `applyDelta` 对变化会话仍保存完整会话。先测长会话带来的复制与序列化成本；仅当它成为主要负担时，再设计追加式保存与定期整理，保留迁移、崩溃恢复、重复处理和回退能力，不立即重做全部存储。
- 任务过程面板只常驻摘要和最近内容，完整大结果按需读取。界面截短与原始记录保存分开；诊断和审计需要的原始记录不能静默丢弃。需要保留多久另设明确策略。
- 检查网页与插件关闭时，监听、计时器、对象和连接是否释放。没有任务依赖的闲置网页可以进入休眠；含未提交表单、音视频、上传下载或自动操作的网页不自动销毁。
- 验证已有本地模型和语音闲置释放实际生效。若负载来自本地推理，再评估并行度与释放等待时间；保持审批判断与任务能力，不能用绕过审批或终止后台任务换取低占用。

## 6. 第四步：长对话只展示当前需要的部分

在前面优化后，若页面元素数量仍拖慢使用，再实施分段加载或可视区域渲染，预计另需 3—5 个工作日。

从“最近消息＋向上加载历史”开始评估，必要时再做动态高度的可视区域渲染。消息数据可以完整检索，页面只保留附近内容；定位远处消息时先加载再滚动。现有 Linux 特殊显示规则有兼容原因，不能直接打开隐藏绘制开关作为修复。

必须单独检查：输出时跟随底部；用户上翻时不被拉回；图片、公式和图表变高后位置稳定；搜索跨历史定位；引用注释；连续选择和复制；导出与无障碍阅读。功能不满足时暂缓该批次，保留前面收益。

## 7. 验收目标与回退

以下是**建议采用的工程目标，不是本次实测收益或保证值**。第一步完成后固定目标硬件和测量口径，再锁定绝对门槛。CPU 统一报告应用进程树的 CPU 时间增量除以墙钟时间，100% 表示占满一个逻辑核；同时注明整机逻辑核数。

| 范围 | 建议目标 | 判定方法 |
| --- | --- | --- |
| 无任务静置 | 应用 CPU 平均不超过 3%，第 95 百分位不超过 5%；会话无变化时不重复写正文 | 预热后记录 5 分钟，渠道轮询和定时任务单独说明 |
| 600 条历史下固定输出 | 同机 CPU 时间较优化前下降至少 30%；输入和切换反馈的第 95 百分位不超过 100 ms | 固定回放、相同输出速度，功能结果相同，三次取中位数并保留波动范围 |
| 长对话界面 | 若实施按需展示，在内容类型相同的前提下，2000 条历史的页面元素数不随历史数量近似等比例增长 | 同时检查滚动、搜索、复制和引用准确性 |
| 内存 | 优先争取相同工作负载下稳定占用降低 20%；反复打开关闭后不持续增长 | 用应用进程树 PSS 比较；关闭后等相同时间；不能仅凭一次下降认定无泄漏 |
| 磁盘 | 没有变化时不重写会话正文；记录与保存合并后，典型长任务写入量争取减少 50% | 按文件类别核对字节量，排除模型下载；不通过延长恢复窗口达标 |
| 任务结束 | 普通云端任务结束后 30 秒内 CPU 回到相应静置范围 | 本地模型内存按现有 5 分钟、语音按现有 3 分钟释放周期另测 |
| 功能完整性 | 消息无丢失、重复、串会话；保存重启一致；审批、停止、唤醒、后台任务正常 | 对照固定预期结果，保存失败及崩溃恢复要覆盖 |

若某项优化没有稳定收益，就不因“结构更好看”而扩大改动。出现丢消息、位置错误、保存失败、审批或任务行为变化，先回退对应批次。性能开关只控制展示或缓存策略，不能成为降低安全要求的开关；涉及存储格式时须先验证备份与旧版本读取/恢复路径。

交付每批改动时保留：版本号、目标硬件和设置、复现场景、三次原始数据、前后比较、功能检查结果、已知边界及回退方法。预计总工作量约 6—9 个工作日完成测量和前两批；需要长对话按需展示时再增加 3—5 个工作日。该估算不包含目标设备不可用或底层兼容问题的等待时间。

## 8. 方法依据

Electron 官方建议先测量运行中的热点，再逐项处理资源占用；延迟非必要加载、避免阻塞主进程和界面线程也是本方案的取舍依据：[Electron 性能指南](https://www.electronjs.org/docs/latest/tutorial/performance)。

界面基准使用的 React 渲染计时只描述相应组件树的渲染成本，不能替代整机 CPU、内存和完整交互测量：[React Profiler 说明](https://react.dev/reference/react/Profiler)。
