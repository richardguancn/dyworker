# “替我审批”的架构复核

核对日期：2026-10-18。后续实现及验收见 [重构交付记录](2026-10-18-approval-implementation.md)。目的：依据五个项目的真实设计，解释 DYWorker 为什么反复要求人工审批，确定重构边界。用户截图是症状和后续回归材料，不是新增白名单的依据。

本报告取代此前“修复若干误判即可完成重构”的结论。本轮没有继续调整生产审批规则。研究期间工作区 HEAD 已推进到 `b834617`，其中含前一轮草稿；本文区分原有问题、已改动的局部路径和仍未解决的结构问题。未替换已安装应用。

## 一、结论

DYWorker 的“替我审批”目前主要是**在人工审批流程后面加一个模型，尝试替用户点允许**。任务授权、敏感信息提示、程序实际访问边界、审核故障、人工确认仍混在几套流程中。它不是一套从入口到执行一致的自动审批模式。

仅把敏感路径改成“可交审核”、延长超时、增加已批准命令缓存，都不能解决这个结构问题。把每一步都交模型也不是必然错误：DSH 就逐调用审核。真正要保证的是正常工作无需人逐步确认，同时操作不能越过实际授权与执行边界。

五个项目并没有统一方案。建议以 Codex 的“执行边界与审批分离”为主结构，采用 DSH 明确区分普通工作和额外授权的判断方法；参考 ZCode 的权限声明、OpenWorker 的来源标记与审计。Pi 用于理解隔离边界，不能被说成已有一套自动审批算法。

## 二、逐个核对

以下为固定版本源码结论，不代表已对这些应用做运行体验测试。

### DSH

版本：`687f282e8625c6b8d11ff58211a90524be2e4317`。

- 实验性 Auto 模式逐次审核工具调用；普通项目读写、分析、测试、构建等属于低风险，政策明确要求不再索要额外明确授权。
- 对既有对象的不可逆删除、生产操作、外部写入等，按动作、目标和范围核对明确授权；敏感信息跨信任边界泄露始终拒绝。
- 评审材料区分人类指令、父任务指令、约束、检查点、事实。事实能证明做过什么，不能变成授权。
- 审核拒绝在 `ask` 策略下交人工；技术失败返回工具失败，不执行。失败与人工审批不是一个状态。
- Auto 使用 Full access 的执行设置，本身不提供文件隔离；PTC 程序内直接 Node 效果也有覆盖限制。不能只抄“低风险允许”而省略这项代价。

来源：[实现](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/experimental/auto-review/src/index.ts)、[范围与限制](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/experimental/auto-review/README.zh.md)。

### ZCode

版本：`aac4755666d09fdcd70272fcf063c077a639015f`。

- 权限服务结合模式、工具能力、项目规则和会话授权决定执行、确认或拒绝。
- `alwaysAsk` 是独立的工具确认声明；其会话授权可以复用。规则有明确优先顺序，不能笼统概括为所有模式都先检查项目禁止。
- `yolo` / `guarded` 的普通调用可直接允许，但特殊确认、计划限制、危险命令分支仍有各自规则。
- **此版本 `auto` 明确未实现，并直接拒绝。**不能把 ZCode 的宽松模式称为成熟的模型自动审批。

适合借鉴的是能力声明、授权范围和模式契约，不是照搬模式名字。

来源：[权限服务](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/apps/zcode-cli/packages/core/src/permission/service.ts)。

### OpenWorker

版本：`5bf0d2fb8c728932fdbc6b49a24113aebc2a4ddd`。

- 它的自动审核确实是人工审批流程中的一层：只能把需要确认的操作变为允许，不能覆盖硬拒绝或 `human_only`。
- 审核政策明确偏向不确定；服务故障、超时、超长材料都可能成为 `unsure`，交给人工。这种设计并不保证用户所期望的连续自主工作。
- 审核输入保留用户原话、已批准的工作说明和执行环境来源。不会检查引用脚本正文，因而不透明脚本仍可能需要人工。
- 当前 Auto 模式不直接复用所有会话内点击产生的授权；配置允许规则与会话授权有区别。
- 它另外提供隔离运行能力。README 对底线的概括与源码的危险绕过模式存在细节差异，应以具体模式实现为准。

DYWorker 的 `evaluateApproval` 和 `risk.mts` 明确注释借鉴 OpenWorker。不能再把这套“宁可多问”的模式当成用户目标的自然答案。

来源：[权限服务](https://github.com/andrewyng/openworker/blob/5bf0d2fb8c728932fdbc6b49a24113aebc2a4ddd/coworker/permissions.py)、[审核器](https://github.com/andrewyng/openworker/blob/5bf0d2fb8c728932fdbc6b49a24113aebc2a4ddd/coworker/reviewer.py)、[授权材料说明](https://github.com/andrewyng/openworker/blob/5bf0d2fb8c728932fdbc6b49a24113aebc2a4ddd/docs/approval-guidance.md)。

### Codex

源码版本：`8c076942cb70fba8e5c4732c23f1faabc4aed484`；官方文档按本次访问日期。

- 执行环境的文件、网络限制与审批策略分开配置。默认允许范围内的执行不必全部经过审核；越界请求，以及规则或工具设置要求确认的调用，才进入对应审批。
- Auto-review 替代符合条件的人工审批，不取消原有执行边界或组织限制。
- 审核依据实际风险、用户授权和当前事实；正常使用已有认证不等于探测秘密，目录在工作区外也不自动意味着高风险。
- 审核器能够做受限只读检查；当前源码有专门的上下文预算、保留指令、版本和检查点处理，不能简化为“每步重新读完整聊天”。具体路径受功能开关影响。
- 明确拒绝、超时、取消分别处理；连续拒绝会中断当前回合，避免不断寻找绕过办法，不是无期限把后续每一步都改成人工确认。

来源：[官方 Auto-review 说明](https://learn.chatgpt.com/docs/sandboxing/auto-review)、[执行隔离](https://learn.chatgpt.com/docs/sandboxing)、[审核政策](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/prompts/templates/guardian/policy.md)、[上下文预算](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/guardian/input_budget.rs)、[上下文版本](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/guardian/review_session_context.rs)。

### Pi

版本：`482c1381a00d8d00bc81697e4a980c593db6803e`。

- 默认不对每次工具调用请求批准；进程及扩展通常拥有启动账户的权限。
- 项目信任控制资源加载，不限制工具实际可以访问什么。工作目录也不是安全边界。
- 官方建议通过容器、虚拟机、操作系统账户等限制访问。仓库中的 permission-gate 是扩展示例，不应误当作默认完整权限系统。

来源：[安全说明](https://github.com/earendil-works/pi/blob/482c1381a00d8d00bc81697e4a980c593db6803e/packages/coding-agent/docs/security.md)、[确认扩展示例](https://github.com/earendil-works/pi/blob/482c1381a00d8d00bc81697e4a980c593db6803e/packages/coding-agent/examples/extensions/permission-gate.ts)。

## 三、DYWorker 的根因与证据

### 1. 风险提示、不可覆盖的规则和人工确认没有清楚分层

`evaluateApproval` 先把 `hookRequiresApproval` 变成 ask；调用方再用 `reviewable` 决定是否允许审核助手接手。历史敏感路径插件只因出现路径就制造人工专属要求。这是截图的直接路径，但其根因是插件没有表达“风险事实”“用户强制确认”“不可执行”的统一契约。

前一轮草稿把命令中的敏感引用交给审核，只修了一个入口。其他调用、模式和人工专属条件仍各自判断，不能据此宣称重构完成。

### 2. 用工具表达方式代替操作影响，导致体验不一致

当前 `write_file(result.txt)` 可直接 allow；等价的 Python 写文件命令先得到 ask，随后才可能交审核。这不一定是单项漏洞，但说明普通工作的可执行范围没有统一定义。不能靠不断列出 Python、Node、测试命令解决。

### 3. 普通执行器缺少独立的进程访问边界

`Workspace.runCommand` 直接启动 shell，设置 cwd 但不由该执行器限制读写或网络；路径提取只是调用前检查，不能约束动态生成的路径。机器人也使用此执行器。

实际诊断在临时目录创建“工作目录”和旁边的假数据文件，关闭临时目录信任。路径检查判定未授权，但通过该执行器启动的程序仍读到了旁边文件。没有读取任何真实私密文件。

范围限定：这是普通执行器的验证；DSH 原生工具/PTC 另有 sandboxPolicy，不能把结果推广成整个产品所有执行路径都没有隔离。恰恰需要统一核对不同路径的覆盖范围。

### 4. 授权状态依赖反复重读聊天；分页无法可靠恢复时序关系

`buildReviewContext` 将最新用户消息放在前面，再拼接历史、事实等文字。`reviewAllContextPages` 把文字切页、分别判断，然后任一 deny 胜出，任一 ask 就转人工。

这不是一个能正确消解“撤回旧限制”的授权状态模型。诊断将明确撤回放在首页、旧限制放在另一页，用受控页面结果证明合并器没有跨页消解阶段。它也把正常工作是否允许与“某页能否引用足够完整的授权”绑定。

分页仍共享 30 秒总时限，请求数量随资料增加。它可能增加长任务等待和失败机会，但没有线上时序证据，不能断言用户截图的某次超时一定由分页造成。

### 5. 审核能力与产品承诺不一致

本地 0.6B 审核器即使给出 allow，当前实现仍强制转换为 ask。这是已有安全校验的结果，不能简单删掉；但这样的服务不具备“替我审批”的完整能力，不应作为等价选择悄悄退回逐步确认。

这不是对截图当前所选模型的推断。诊断只是证明该产品分支存在必然转人工的行为。

### 6. 审核失败、拒绝、缺少授权的处理不统一

前一轮把部分在线服务故障改为工具失败，是局部正确方向。但本地异常、格式无法恢复、材料容量不足等还可能返回 ask。桌面、DSH、机器人又分别维护审核资格和结果处理，容易产生不同结果，例如机器人将所有 `delete_file` 排除出自动审核。

### 7. 之前的验证不足以证明“替我审批”有效

大量测试使用预设 allow 返回，能证明流程会不会弹窗、是否执行，却不能证明真实模型理解任务边界。增加截图案例并得到绿色测试，不能证明对陌生任务仍然可靠。上次的测试结论不应被当作重构完成。

## 四、应采用的重构契约

这部分是依据比较提出的 DYWorker 设计建议，并非声称其他五个项目都这样实现。

1. **先定义模式承诺。**“替我审批”表示任务范围内的正常工作由系统决定；用户明确保留的确认、新增权限、重大且未授权的影响才找人。不是免除检查，也不是默认逐步确认。
2. **执行限制独立生效。**统一普通任务、DSH、机器人对文件、网络、进程的执行限制和越界申请方式。只有具备可强制执行的边界，才能稳定减少常规审批。
3. **建立有来源、有版本的授权记录。**保存用户任务、资源范围、明确限制、人工授权的作用域和有效期；新指令更新版本，旧审核结果随之失效。不能从助手计划、网页或模型总结推导新权限。
4. **一次操作只有一个统一判断入口。**工具声明提供结构化影响，命令保留完整原文、工作目录、入口脚本和已核实事实。风险提示作为证据，显式用户规则作为规则。未知不能被静默当作安全，也不能因工具名字陌生直接变成人工专属。
5. **风险与授权分开判断。**普通、可恢复的任务内工作默认可进行；新增外部影响和不可逆操作核对具体授权；秘密外泄等按目标政策拒绝。先检查事实，必要时由受限只读检查补齐，不立刻把缺失信息甩给用户。
6. **明确结果类型。**允许、政策拒绝、需要新增授权、审核服务不可用、用户取消分别流转。故障不执行，有界恢复；仍失败时报告任务受阻，不能假装缺少用户许可，也不能无限重试。
7. **能力不足应显式降级。**不可靠审核器不能显示为与完整自动审批等价。模型选择需基于独立评测，不能用强制转人工掩盖能力缺口。
8. **撤换案例驱动的例外和逐页投票。**在统一入口与授权记录就绪后迁移旧逻辑，保留必要安全回归；不要继续往旧函数追加程序名、配置名和路径特殊规则。

## 五、完成标准与后续实施顺序

先实现共享决策与授权记录，再接通一致的执行边界和故障状态，最后迁移各运行入口与界面。不可仅完成前半项就宣布“少弹窗”交付。

验收使用与用户截图无关的多类完整任务，并改变工具表达、目录、命令语言、消息长度、授权先后、运行入口和模型服务状态。至少检查：

- 范围内连续读写、验证、临时文件恢复不反复人工确认。
- 明确撤回、重新授权、授权过期，以及审核等待中改变指令都按当前有效授权执行。
- 直接文件操作与等价脚本在相同实际影响下结果一致；动态生成路径仍受实际执行限制。
- 正常认证与秘密暴露分开；混合命令、重定向、网页诱导和不透明脚本不能借常规工作放行。
- 服务超时、认证失败、非法回复均不执行、不制造虚假的授权问题；取消后迟到允许无效。
- 除流程测试外，真实审核服务评测必须记录误放行、误打断、等待时间；覆盖完整任务和陌生场景，不只检查单条命令。
- 对运行中的应用做完整任务验收，明确安装版本。源码测试通过不能代替这一项。

## 六、本次实际验证

运行 `node scripts/verify-approval-architecture.mjs`，四项结构诊断均复现。脚本只使用临时自拟文件与受控审核返回，不读取真实配置，也不请求在线模型。输出保存在同目录 `2026-10-18-approval-architecture-evidence.json`。

这些证据证明当前结构问题，不能证明线上审核准确率、用户截图的服务耗时原因，或已安装应用已修复。五个上游项目为源码和官方文档核对，没有假称逐个安装实测。
