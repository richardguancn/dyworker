# 任务内停止程序仍转人工：修复与验证

日期：2026-10-20。

## 原因与目标

上一轮重构保留了 `isReviewerEligible` 中对 `kill`、`pkill`、`killall` 的人工专属限制。即使用户选择“替我审批”，这些命令仍直接进入人工确认，而不是检查当前任务的目标和授权。截图说明的是同一类进程管理缺口，不能通过为具体项目名称加白名单解决。

完成标准：任务内具体程序的正常停止和自产缓存清理能持续完成；名称匹配先核实并缩小目标；其他项目不受影响；事实不足不冒充需要新增授权；审核期间目标变化时旧允许失效。保留用户明确确认规则、拒绝修改模式、其他既有危险命令限制和禁止形成长期通配授权的规则。

## 实现范围

- 进程信号可进入已有任务审核，仍不保存为常驻允许规则。普通任务、DSH 和机器人复用同一入口。
- 共享只读检查使用系统工具查询具体进程的编号、父进程、所属账户、启动时间、程序路径和工作目录。不读取进程环境，也不输出完整命令行。
- 目录相同只是位置事实，不能据此证明由本任务启动；审核继续核对用户原话与实际启动记录，并看到完整操作中的其他删除、写入等影响。
- 名称批量停止不直接执行，也不直接弹人工卡。返回匹配事实给任务助手，先缩小为具体进程编号。没有匹配时可跳过停止步骤；事实不全时继续只读调查。只有确需影响任务外对象且缺少对应授权时才交用户决定。
- 具体编号的审核得到允许后，再查一次目标身份和目录；发生变化时旧结论作废。事实不足单独返回 `needs_evidence`，与拒绝、人工授权、服务故障和取消分开。
- 新模块加入审批逻辑文件自身的保护范围。

## 实际验证

1. 新建两个临时项目，分别启动带相同随机标记的测试程序。只读检查准确区分当前项目和另一个项目，不输出测试参数中的假秘密。
2. 程序化连续流程从批量匹配转为具体编号，实际停止本任务程序、删除自产缓存，另一个项目程序保持运行，人工审批零次。
3. 使用应用安全存储中的已有模型配置进行真实模型验证。先提供真实批量检查返回，再由真实模型继续任务；任务与审核请求均使用当前配置中的真实服务。仅发送自拟临时场景，未读取业务文件，未输出凭据。
4. 真实模型完成后，验证程序独立检查本任务子程序已退出、缓存目录已不存在、其他项目子程序仍存活，人工审批零次。不是仅依据模型最终回复判断成功。
5. 检查审核期间目标退出、动态编号、进程组、未解析选项、取消，以及普通任务、DSH、机器人三条路径。明确人工规则和其他危险命令限制继续有效。

真实模型结果见 [验证记录](../verification/process-approval-2026-10-20/live-result.json)。可复现入口：`scripts/verify-process-approval-live.cjs`；它只创建并清理自己的临时程序和文件，通过应用正常安全存储使用当前配置，不打印凭据。

## 最终检查结果

- 11 组相关检查按项目规定的 `--test-concurrency=1` 运行：388 项通过，0 失败、0 取消、0 跳过。包含进程专项、代理执行、远端审批、授权连续性、故障恢复和三条审批入口。
- 一次同时运行构建与并行检查时，既有四十步用例超过原有 30 秒限时。随后按项目的串行方式完整重跑，全部通过；没有提高用例限时、跳过检查或放宽权限预期。
- 本地主进程构建及差异格式检查通过。最后补查 DSH 的工具前缀，确保实际前缀不会跳过进程检查。

## 边界

- 运行验证在 macOS 完成。Linux 使用 `/proc` 查询目录，但本次未在 Linux 或 Windows 实测；Windows 没有此只读入口时不会猜测目标或直接放行。
- 只读检查覆盖可解析的直接进程信号调用；不是通用 shell 解释器。动态目标、复杂选项等不能完整解析时要求继续核实。其他包装脚本仍受原有完整任务审核约束，不能宣称已实现任意脚本中的进程访问隔离。
- 身份复查降低审核等待期间对象变化的风险，不是与发送信号绑定的操作系统原子句柄，不能声称消除了全部竞态。
- 本次修改源代码并更新本地构建产物；未替换已安装应用，未提交或发布。
