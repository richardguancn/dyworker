首次调研：2026-10-31；原文补核：2026-11-01。结论针对调研时的工作区，包括当时已有的未提交修改；不代表已发布安装包的状态。本次仅新增和更新调研材料，未接入新功能。

**结论：值得借鉴，优先补齐任务管理，暂不整包接入。**

DYWorker 已有模型执行、多个助手协作、微信/QQ 接入、定时计划、任务续跑、审批和执行记录。上游最有价值的增量，是在这些能力之上管理“哪件事由谁提出、允许做到哪里、后续消息交给谁、现在等什么、怎样恢复和交付”。建议沿用现有执行能力，先增加统一任务记录与可靠消息处理，再增加自动分派和有限的主动工作。

补读原文后，产品目标应进一步明确：用户面对统一的接待入口，各项工作在独立环境中推进，用户无需自行记住每个会话的背景。可靠保存是基础，同时还需建立明确的分派职责、运行中接收修改要求、按需找回旧资料和进展检查，不能把升级仅理解成消息队列改造。

直接安装上游不能等同于完成接入：它是围绕一个 GitHub 仓库工作的研究原型，默认执行方式、依赖版本、界面和业务结束条件都与本项目不同。[上游定位](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/README.md)

**上游真正解决的问题**

| 机制 | 已核实的行为 | 对 DYWorker 的意义 |
| --- | --- | --- |
| 分派与执行分开 | 主会话判断和分派；每项工作有独立执行会话和目录 | 接收新需求不必等待已有工作全部结束；普通任务仍可走原入口 |
| 消息与任务分开 | 一条消息有稳定标识；一个话题可以关联多个任务；关联资料本身不授予权限 | 手机连续补充材料时，能区分原任务补充和另一件事 |
| 授权随任务保存 | 记录来源身份、规则版本、范围和明确/推断依据；恢复已结束任务时重新校验 | 不必从整段聊天猜测“最初到底让做什么” |
| 后续消息有明确归属 | 已交给执行者处理的人类补充，主会话不能同时再开一单；超范围可以交回重新判断 | 减少重复派工和两个助手抢同一件事 |
| 先保存、后执行 | 任务变化与待执行动作一起保存，再启动、投递或回复；失败按间隔重试 | 断网、重启后可恢复待办，减少漏执行和漏回结果 |
| 人工处理状态明确 | 区分等待答复、等待审阅、受阻、失败、排队、工作中和等待外部消息 | 用户可以先处理真正卡住的任务 |
| 主动工作先观察 | `observe` 只记录推断出的候选工作，不执行；`auto` 需匹配已启用规则 | 先检验“它会不会乱接活”，再开放有限自动执行 |

**最适合的落地场景**

1. **手机派活与补充材料，优先试点。** 假设用户先说“整理本周材料”，随后发附件和“按上次格式”，这些消息进入同一任务；再说“另外检查另一份表格”，系统创建另一项工作。结果回到原聊天，并能从桌面找到文件。多个任务并存且归属不清时，给出简短选择，不能凭相似文字把事情合并。
2. **持续跟进资料与待办。** 假设用户明确指定一个文件夹并要求“材料齐了生成周报”，只监控该范围；资料未变时不反复询问模型，不发无变化提醒；资料到齐后生成草稿，缺关键材料时列明缺项。现有定时能力可承担检查触发。
3. **机器人团队共同完成一份成果。** 资料整理、撰写和核对可分工，但全部关联同一任务、来源与最终成果。先让普通执行服务承担主任务，后续再给机器人团队增加接入方式，避免第一版就同时改动两套运行环境。
4. **为 DYWorker 自身开发提供辅助，单独部署试验。** 上游最直接适用的场景是受理 GitHub 问题、复现、修改并提交供审阅的结果。若试验，使用独立账号与执行目录；它是研发辅助工具的试验，不等同于给办公产品增加完整功能。

**建议的接入方案**

入口（桌面、QQ/微信、定时计划）→ 保存来件 → 确认授权与任务归属 → 创建或更新任务 → 交给现有执行服务 → 保存结果与待发送消息 → 原渠道交付／收件箱等待人工处理。

轻量问题、明确指定会话的用户输入可以直接进入已有任务，不要求每条消息都经过额外模型判断。仅在确实需要区分新任务、补充和关联时调用分派模型，避免平白增加等待和费用。

建议新增的内部职责如下；名称是设计建议，不是已经存在的代码：

| 职责 | 保存或处理的内容 | 复用位置 |
| --- | --- | --- |
| 任务记录服务 | 目标、验收条件、来源、授权范围、状态、当前执行会话、成果、等待原因 | 宿主服务装配、现有会话存档和目标状态 |
| 来件记录 | 来源实例、聊天/话题、消息标识、发送者、原始内容、处理位置与归属 | 现有渠道适配器、定时计划入口 |
| 待执行动作与发送记录 | 待启动、待补充、待发送；尝试次数、下次时间、已完成标记 | 现有执行服务和回复能力 |
| 分派判断 | 新建、补充、停止、忽略或等待澄清；保留判断依据 | 首期用明确指令与任务选择，随后加模型判断 |
| 人工处理清单 | 待确认、待补材料、待审阅、失败；显示下一步可以做什么 | 现有收件箱和任务页面 |

任务授权与工具审批要分开：前者回答“为什么可以做这件事”，后者回答“这一步操作是否允许”。读到群消息、附件、网页或其他任务内容，只能增加上下文，不能扩大授权。上游对运行中任务的策略变更采用通知而非立即取消；DYWorker 应明确设计撤权行为，不能照搬后声称权限已经即时撤回。

并行执行首先限定为不同目录或独立成果文件。同一文件的写入继续排队；控制鼠标、键盘和前台窗口的工作共用一个独占位置。任务目录分开并不能隔离同一台电脑的桌面操作。

外发恢复采用稳定消息编号和发送记录，但不承诺所有平台“绝不重复”：若远端已收件、本地还未记成功就中断，重试仍可能重复。接入时需利用渠道支持的去重能力或查询结果；无法确认的外部动作应先核对状态。上游的恢复提示也要求检查既有外部结果后再继续。

新增保存结构应尽量独立，以便停用新功能后原任务仍可运行。如果涉及数据库 SQL 变更，统一维护在项目选定的单一版本脚本中，不新建零散 SQL 文件。

**不建议直接照搬的部分**

- **无需审批的默认执行方式。** 上游明确写明，执行会话以操作者的系统身份运行命令且不弹审批；独立目录和命令包装不是安全隔离。办公场景必须保留 DYWorker 现有权限检查和人工确认。[执行限制](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md)
- **围绕代码合并设计的完成规则。** 办公任务应按文件生成、内容校验和用户验收判断，不按代码请求是否关闭判断。上游自动合并要求主要是提示词规则，也不能作为本项目强制权限保证。
- **整套网页界面与默认安装流程。** 本项目已有桌面页面、设置、审批和插件入口；重新并入一套独立控制台会出现重复入口和状态。
- **把云端常驻、远程执行、独立智能监工当作本次已经拿到的能力。** 本次没有验证这些能力可由公开原型直接提供。退出应用或电脑离线后的持续执行，需要单独的运行服务与部署方案，应后置评估。

版本方面，双方 Cordis 都是 `4.0.5-alpha.1`，但本项目 DSH 核心依赖为 `0.2.1-alpha.1`，原型要求 `^0.2.1-alpha.2`；原型还依赖本项目未直接声明的网页服务、会话控制和界面包。本项目 React 为 `19.2.0`，上游开发依赖为 `18.3.1`。这些是兼容性验证事项，不能仅凭“都使用 DSH”判断可直接加载；React 版本不同本身也不是必然不兼容的证明。[上游依赖声明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/package.json)

适合优先参考的源码是 `src/core/`、`src/app/effects.ts`、`src/app/outbox.ts` 和相关测试；接入现有执行服务与桌面界面的部分需要自行适配。若复制代码，应保留其 MIT 许可证和版权声明。

**实施顺序与验收条件**

| 顺序 | 范围 | 交付标准 | 相对工作量 |
| --- | --- | --- | --- |
| 第一阶段：可靠接单 | 先选一个渠道；来件、任务、待执行动作和结果发送长期保存；现有执行服务照常工作 | 同一消息重放只建一个任务；保存后、执行前中断可恢复；发送失败后可重试；人工停止后不被补发事件复活 | 中等，涉及入口、保存与恢复，不能当成只改提示词 |
| 第二阶段：自动归属与人工处理 | 分派者不亲自处理长任务；新任务/补充消息分流；按需找回关联资料；运行中接收修改；集中展示人工事项和基础进展检查 | 两件事在同一聊天不串；确定归属的补充直接进入指定任务；耗时工作不阻塞新请求；等待审批让出执行容量；拒绝和权限变化可追溯 | 中等偏高，重点是边界和竞态验证 |
| 第三阶段：有限主动工作 | 一个用户指定目录或已授权来源；先观察，后允许生成草稿 | 未授权不启动；无变化不提醒；重复事件不重复生成；来源停用和预算耗尽时停止自动接活 | 中等，必须建立第一阶段的可靠性基础 |
| 后续再评估 | 机器人团队统一调度、GitHub/飞书来源、离线常驻、跨设备执行、允许主动干预的独立监工 | 分别建立独立的权限、恢复、费用与效果验证 | 较大，当前不承诺工期 |

主动模式建议分为“关闭／只观察／允许执行”。即使开启允许执行，也先限定为检查和草稿生成；发消息、提交正式资料等动作继续遵守原授权与审批。来源、目录、允许动作、并发数和用量上限应可检查，而不是只写在提示词里。

试点建议记录：重复任务数、丢失来件数、任务错配数、恢复成功率、外发重复数、每项任务的人工介入次数与模型用量。对比升级前后处理同一组代表性任务的结果，再决定是否扩大范围；本次没有测得提升百分比或节省费用。
