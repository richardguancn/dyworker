# 运行中 CPU 与内存异常占用排查

日期：2026-10-20。初次排查范围：本机正在运行的 `/Applications/DYWorker.app`，主进程 PID 38660。初次排查只诊断，未修改产品代码、安装包、用户设置或任务状态，也未重启应用。用户随后确认修复，实施与安装结果见末节。

## 结论

本次持续高占用直接发生在模型回复接收路径。自动唤醒续跑收到一份以 JSON 错误对象开头的大回复，程序仍按照流式事件读取，在未找到事件分隔符时不断积存数据，并且每收到一块就从头扫描整个缓冲。缓冲越大，重复扫描和内存分配成本越高。

现场读取到缓冲长度为 **165,000,314 个字符**，正文与思考内容均为 0，尚未收到正常结束或失败事件。开头包含 `247 validation errors`，第一项为 `string_type`，位置为 `('body', 'input', 'str')`。前 64 KiB 中没有实际换行符；尾部为长编码数据片段。只读取了少量格式片段，没有复制或保存完整异常回复、完整图片或明文凭据。

这说明接收的内容是错误详情，不能解释为模型正在正常生成长回复。具体是哪一项请求内容导致服务端校验失败，本次没有完整取得校验结果，尚不能下结论。仅第一项联合类型校验分支的错误，也不足以断言整个接口要求 input 必须为字符串。

由调用路径可知：该回复已通过 `response.ok` 检查，且响应类型包含 `text/event-stream`，因此进入流式读取。未独立记录实际 HTTP 状态码或完整响应头，不把它表述为已直接观测到 HTTP 200。

## 实际验证

1. 连续四次测得主进程 CPU 为 78.9%、82.2%、78.1%、78.9%，随后另一次测得 111.2%。主进程是主要消耗来源；界面与图形进程当时明显较低。
2. 系统 5 秒采样显示该进程物理内存占用约 1.4 GB，历史峰值约 2.8 GB；两次系统采样均集中在同一条网络接收回调路径。
3. 对主进程录制 4 秒函数耗时：3166 个样本中，3012 个落在 `readResponsesStream` 的分隔符搜索行，约 95.1%；加上该函数其余 35 个样本，共约 96.2%。另有 116 个样本在内存回收，约 3.7%。
4. 短暂停下读取上述缓冲长度及格式后立即恢复。调用链包含 `resumeWake` 和 `checkDueWakesOnce`，确认属于自动唤醒续跑。
5. 读取安装包中 `agent.mjs`、`main.mjs`、`remote-messages.mjs`，三者均与本地对应构建文件的 SHA-256 一致。
6. 用真实 `requestModel` 接收路径进行隔离复现，不访问在线模型，不使用用户会话。每次约 32 MiB、每块约 32 KiB，分别输入合法流式心跳加结束事件、缺少事件分隔符的 JSON 错误正文：

| 场景 | 实际耗时 | CPU 时间 | 结果 |
| --- | ---: | ---: | --- |
| 正常流式内容 | 67 ms | 72 ms | 完成 |
| 异常错误正文 | 6932 ms | 7291 ms | 读完后才报告未收到终止事件 |

这是本机各一次的对照，证明该接收路径对异常格式存在明显额外开销，不是安装包修复前后的性能验收。复现程序为本机临时文件 `/tmp/dyworker-stream-repro.mjs`，原始耗时记录来自 `node /tmp/dyworker-stream-repro.mjs`。

## 当前状态与边界

最后一次检查时，异常处理已不在原调用位置。未修改或重启应用的情况下，接下来六次采样 CPU 为 0.8%、0.9%、0.8%、1.2%、0.8%、6.0%，驻留内存约 132～161 MiB。请求为何在此时结束未独立取证，不能断言是超时、取消或服务端主动结束。

负载回落说明本轮高占用与该异常处理有直接对应关系，但不代表缺陷已修复，也不能据此认定存在永久内存泄漏。主进程临时检查入口已关闭，末次检查未发现该进程的 TCP 监听端口。

## 后续客户端修复（2026-10-20）

用户确认修复后，新增 `electron/model-stream.mts`，由 Responses 与 Chat Completions 两条模型接收路径共用：

- 识别以 JSON 对象、JSON 数组或 HTML 开头的异常正文，立即抛出不参与网络重试的格式错误；提示不回显原始异常正文。
- 只扫描新到的片段及前一片段末尾三个字符，按片段保存未完成事件，事件结束后再合并，消除反复扫描完整缓冲的成本。
- 单个事件最多保留 8,388,608 个 UTF-16 单元，超过上限即停止接收；这个限制不作用于整个任务或整段多事件回复。它会拒绝超过该大小的单条合法事件，避免无上限积存。
- 沿用现有取消与收尾路径，识别异常后关闭底层连接。

新增 `tests/model-stream-safety.test.mjs`。最初四项故障检查在修复前全部失败，修复后通过；随后补齐正常正文、思考、工具参数、用量、UTF-8 字节切分、CRLF 分隔符、大小边界、停止与不重复重试检查，共 12 项通过。`tests/agent.test.mjs` 在允许系统命令保护功能的环境下运行，268 项全部通过；受限环境初跑有两项因系统保护无法启动而失败，未将初跑记为通过。

原始 32 MiB 复现程序再次执行：异常输入约 1 ms 即停止，读取两次后取消连接，没有读取剩余异常正文；正常输入仍完整完成。另以固定随机种子执行 3000 组不同片段长度和换行组合的检查，全部内容一致。上述单次耗时受本机负载影响，主要验收依据是停止读取、连接取消和内容完整的断言。

本修复解决客户端因异常回复持续高占用的问题，不声称解决服务端的请求校验错误；服务端的具体校验原因仍需另外取得证据。
