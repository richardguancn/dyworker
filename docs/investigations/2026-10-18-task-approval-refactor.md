# 替我审批：长任务连续执行重构

日期：2026-10-18。目标是让授权任务中的正常步骤由程序与审核助手处理，人工确认只承接明确要求确认的操作及无法解决的授权缺项。不是关闭权限检查，也不是给解释器或目录无限授权。

## 验收标准

- 长任务超过旧的单次审核预算后，继续完整核对，不因资料长度把所有后续步骤交给用户。
- 截图中的查找、编译、测试、临时改写与恢复、假凭据检查、保存模板能连续处理。
- 较早禁止、真实秘密访问、用户强制规则、取消和超时仍有效。
- 普通任务、DSH 和机器人不能因前三个操作被拒绝而停止审核后续操作。
- 本地实际执行与真实服务验证分别记录，不把模拟模型结果当成真实模型验收。

## 四个项目的实现取舍

### DSH

核对官方 master 提交 `687f282e8625c6b8d11ff58211a90524be2e4317` 的 [自动审核实现](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/experimental/auto-review/src/index.ts) 和 [说明](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/experimental/auto-review/README.zh.md)，也核对本项目安装的 `0.2.1-alpha.1` 权限与审批包。

DSH 把沙箱范围、审批策略、自动审核应答分开。自动审核是实验选项，使用当前任务模型逐次检查实际影响；普通项目操作与有证据的本次临时产物清理属于低风险。历史输入保留来源，助手正文和工具结果不会成为授权。它仍逐次审核，并没有实现“一次批准所有未来操作”；超出模型容量会失败。

可借鉴的是权限边界与审核应答分层，以及区分用户要求和事实。不能把 Full access 执行误解为自动审核本身提供了隔离。

### ZCode

核对官方提交 `aac4755666d09fdcd70272fcf063c077a639015f` 的 [权限服务](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/apps/zcode-cli/packages/core/src/permission/service.ts) 和 [命令规则](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/apps/zcode-cli/packages/core/src/tool/handlers/bash-command-permission-policy.ts)。

权限服务区分模式、工具能力、项目规则和必须确认的操作。命令规则会分析复合调用、为稳定动作生成规则；无法安全概括时退回精确命令。所核对版本中的 `auto` 分支明确未实现，不能把它宣传为成熟的模型代审批；无提示执行主要来自其他模式。

可借鉴的是结构化操作影响和精确规则边界，而不是把 Python 或任意命令前缀一概批准。

### OpenCode

[官方文档](https://docs.opencode.ai/docs/permissions/)说明 allow/ask/deny、规则优先级和确认选项。另核对 dev 提交 `8c173a8f3805d8e749d44311054b07e37a1b2ce1` 的 [权限服务](https://github.com/anomalyco/opencode/blob/8c173a8f3805d8e749d44311054b07e37a1b2ce1/packages/core/src/permission.ts)。

实现先处理禁止规则，再评估资源范围；用户选择 always 后会重新评估已排队的请求。注意版本差异：文档描述会话内规则，而这份 dev 源码把保存规则关联到 projectID，不能笼统声称所有版本都只保留到会话结束。

可借鉴的是规则变更后的重新判断与等待队列处理。DYWorker 本次没有自动生成更宽的长期授权。

### Pi

核对 [官方安全说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/security.md)。Pi 默认按启动账户的权限执行，不逐工具请求批准。项目可信设置控制启动时加载的项目资源，并不限制后续工具能访问哪些文件；限制主要依赖操作系统或隔离环境。

这解释了它为什么顺畅，但不能直接套用于带账户连接、办公数据和对外操作的 DYWorker。

## 本地确认的根因

1. 普通在线审核完整输入超过估算 24,000 token 就直接转人工，后续操作继续携带同一长历史，因此反复触发。不是某个 grep 或测试本身需要再次授权。
2. `.venv/bin/python` 的链接目标在工作区外，会被当成待授权的数据路径。
3. 受保护文件检查扫描模板正文，把“保存说明中提到 .env”混同于当前读取 .env。命令中的 `.env.example` 也进入不可代审分支。
4. 普通任务、DSH、机器人都有连续三次拒绝后停止自动审核的行为。
5. 同一操作缓存折叠空白，会把引号内有不同空格的命令混为一条。

## 本次变更

长任务增加共享的分段审核：原文不摘要、不丢弃，页边界有重叠并带来源提示；每页仍看到完整动作、接口和访问说明。只有所有页面无冲突、至少一页给出可在该页原文核对的授权引用时才能允许。禁止和不确定结论优先，缺失、伪造引用及格式错误均不放行。并发最多三页，沿用总时限；一组失败后停止发起后续页，审核结束会取消在途请求。

取消三次拒绝后对整个任务的人工降级。单次拒绝仍拒绝本次操作，后续动作继续审核，原有重复工具调用防循环机制保留。

虚拟环境仅在命令的程序位置识别已知系统解释器的真实目标；同一路径作为数据读取参数仍检查。没有把 Frameworks、Cellar 或 Python 能访问的目录加入授权。

保存模板只保存正文，不因正文提到秘密路径而直接强制人工；仍须正常任务授权审核。命令中仅出现配置示例时允许审核助手核对，真实 `.env`、私钥、混合命令和用户强制规则保持保护。示例名称不是“绝不含秘密”的证明，也不直接放行读取。

缓存现在保留完整命令字节，仍受当前任务要求、入口脚本、工具说明和政策变化约束。没有新增目录授权、解释器通配授权或跨任务授权。

## 验证与边界

本地代表性流程实际执行了 Python 查找、编译、测试、临时修改与恢复、假凭据检查和模板保存。正常流程零人工确认，测试输出与最终文件内容均核对；审核答复由模拟服务提供。

反向检查覆盖旧限制、末页禁止、伪造引用、缺失授权、格式错误、超时、停止、真实秘密路径、混合命令、私人软链接、用户强制规则及三次拒绝后的后续审核。完整检查数量和构建结果见同日期 verification 目录。

真实服务检查未完成：设置中的密钥是应用加密值，首次独立检查脚本误把密文用作认证，请求失败；不能据此认定用户的真实密钥失效。脚本已增加加密检查，禁止再次把密文发出。后续真实验证必须通过应用正常解密后的服务入口。未修改用户设置、未解密或输出密钥。

尚存边界：离线小模型仍只提供建议；完整动作过大、超过 64 页、服务失败、跨页授权冲突无法解决时仍会停止等待确认。分段增加模型请求，不是操作系统沙箱，模型误判风险仍存在。本次不声称真实服务决策质量、已安装应用或所有截图中的完整隐藏脚本均已验证。截图显示不全的联网鉴权脚本没有擅自执行，也未访问真实广告账户。
