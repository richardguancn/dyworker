# DYWorker 采用 Cordis 并支持 DSH 插件：实施评估

评估日期：2026-09-08，2026-09-09 完成复核。DSH 指 DeepSeek Harness。本文是实施前评估，没有接入 Cordis、安装 DSH 插件或修改应用功能。

## 1. 决策结论

**建议有条件实施：先用 Cordis 建立新扩展的管理能力，第一期只承诺经过验证的工具类 DSH 插件。**

采用 Cordis 的价值是统一插件启停、依赖、事件和资源释放，逐步减少新增能力对主程序的直接修改。它不自动提供 DSH 的模型、会话、工具执行、界面和权限能力，所以不能把“引入 Cordis”宣传成“兼容所有 DSH 插件”。

当前尚未指定目标插件，以下按“先工具，再按需求补充记忆、模型与界面扩展”估算；不能给出插件市场的兼容百分比。

## 2. 依据与现状

### 上游事实

- DSH 官方说明所有能力由 Cordis 插件组合，包含模型、工具、会话和执行流程；上游仍是开发预览，明确会发生不兼容变化。[官方说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)
- Cordis 自身也提示接口尚未稳定。[Cordis 官方说明](https://github.com/cordiverse/cordis/blob/main/README.md)
- DSH 有 profile、bundle 和逐层 patch 的装配规则；当前支持的 Node 应用通过 `dsh` 启动。SDK 使用同版本 DSH；`sdk-minimal` 是上游维护的独立组合，并非任意插件都能工作的通用空壳。[官方架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)
- 官方桌面版已经将桌面外壳、匹配版本的后端以及可写插件目录分开管理。DYWorker 可以参考这个边界，但接管整套桌面后端仍是单独的工程。[官方桌面架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md#desktop-application)

上述概览链接随上游变化；固定源码基线为 `c389f96bf3a9b6807cb71ed6bdad5849be0df6d8`。准确版本与固定链接见[上游核查依据](cordis-dsh-upstream-evidence-2026-09-08.md)。已核实 DSH 使用自己的 `@deepseek-ai/cordis` 4.0.2，包含本地修改；不能直接用普通 Cordis 替换。

### DYWorker 现状

本地检查基于提交 `b68502e4e0e2da1ea2891a30e124ffdd48b081a5` 加当前未提交工作区；当时已有的图片和桌面操作相关改动未改动。应用版本为 0.1.23。

| 现有能力 | 实际位置 | 对改造的影响 |
|---|---|---|
| 外部工具定义和执行入口 | `electron/agent.mjs` 的 `extraTools`、`onExtraTool` | 可成为第一期工具桥接入口，避免重做完整任务流程 |
| 外部工具连接及路由 | `electron/main.mjs` 的 `mcpExtraTools`、`agentExtraTools`、`createExtraToolRouter`；`electron/mcp.mjs` | 可复用连接、取消、错误返回的经验，但 MCP 不等于 DSH 插件规范 |
| 风险判断、用户确认、审计 | `electron/risk.mjs`；`electron/agent.mjs` 的 `evaluateApproval` 和工具执行流程 | 新工具必须进入同一约束，且要补齐未知工具默认规则 |
| 桌面、定时、唤醒、聊天渠道分别启动任务 | `electron/main.mjs` 的四类 `runAgent` 调用 | 必须统一接入；只修改桌面对话会造成其他入口能力缺失 |
| 文件型技能发现与合并 | `electron/skills.mjs` | 文本技能与可执行插件应分别管理，不能把插件放进技能目录就算支持 |
| 任务队列、历史、记忆、QQ/微信 | `electron/session-queue.mjs`、`electron/memory-wiki.mjs`、`electron/channels/manager.mjs` 等 | 已有行为需要保持；第一期不迁移历史、不替换渠道处理 |
| 桌面打包 | `package.json`、`electron/main.mjs` | 需新增插件可写目录、运行环境和各平台验证，开发机成功不足以交付 |

主入口、任务执行、主界面分别约 4,664、5,053、10,288 行。行数本身不证明问题，但结合多处独立装配，说明一次性全面重构的影响面较大。

## 3. 路线比较

| 路线 | 可交付结果 | 主要代价 | 建议 |
|---|---|---|---|
| 仅把现有模块整理成 Cordis 插件 | 便于维护和扩展 | 不会因此获得 DSH 插件兼容 | 可作为内部改造，不单独算达成用户目标 |
| Cordis 扩展层 + 有限 DSH 兼容桥 | 少量已验证插件进入现有 DYWorker 任务 | 需要明确支持的依赖和行为，长期控制兼容桥范围 | **第一期优先** |
| 官方 DSH SDK + 独立后端 | 更多依赖 DSH 任务流程的插件有机会工作 | 任务状态、用户确认、历史、计费记录、取消、打包需接通 | 若重点插件依赖完整 DSH，则优先验证此路线 |
| 全面替换 DYWorker 执行体系 | 能更深利用 DSH 的组合能力 | 现有办公、渠道、权限与历史的回归面最大 | 不建议作为第一步 |

SDK 路线同样不能自动支持 DSH 专用界面插件，也不能与 DYWorker 原执行流程同时拥有同一任务的写入权。应按任务选择一个执行后端，禁止两个后端同时推进同一任务。

**复核后的额外限制：** 该基线的 SDK 尚无逐任务取消、会话关闭方法和已启用的服务器向客户端审批请求；放弃轮次依靠关闭运行进程。`sdk-minimal` 默认使用 `danger-full-access`。因此 SDK 路线必须先解决取消、确认和权限，不是直接可替换的成熟后端。依据见[协议和配置核查](cordis-dsh-upstream-evidence-2026-09-08.md)。

## 4. 第一期兼容范围

| 插件类型 | 第一阶段判断 | 放行条件 |
|---|---|---|
| 只依赖 Cordis 基本生命周期、日志的插件 | 较容易 | 核对同一运行时、正确释放资源，无隐藏依赖 |
| 注册查询、转换、搜索等工具的插件 | 优先试点 | 逐项核对工具注册、参数、结果、取消和实际依赖；不能只看插件名称 |
| 文件、命令、网络等工具插件 | 有条件 | 明确副作用与权限，核对是否绕开宿主直接访问系统 |
| 模型提供方插件 | 后续专项 | 对齐请求、流式响应、错误、用量、取消与密钥提供方式 |
| 记忆、上下文整理、任务流程插件 | 后续专项 | 对齐会话事件、持久化和恢复语义，避免重复写入或丢失上下文 |
| DSH 专用侧栏、设置页、聊天组件 | 第一阶段不承诺 | 需依赖匹配的前端运行环境，或改写成 DYWorker 的扩展页面 |
| 整套 profile、preset、替换执行循环的 bundle | 第一阶段不承诺 | 涉及完整运行树；应转向官方 DSH 后端验证 |

支持清单必须记录“插件名 + 插件准确版本/提交 + DSH 版本/提交 + 支持能力 + 验证平台”。依赖缺失、版本不符、界面能力缺失时，安装前显示具体原因，不允许静默加载成一个不起作用的插件。

## 5. 建议设计

### 5.1 扩展运行与主程序的边界

建议让 Electron 继续拥有界面、系统凭据、用户确认和产品数据。新建独立插件宿主，由 Cordis 管理插件生命周期和服务依赖；通过受控通道与主程序交换工具调用和结果。优先使用与选定 DSH 基线一致的 Cordis 发行物，不混装多个不兼容的 Context/Service 实例。

这是 DYWorker 自己的有限兼容宿主，不是官方支持的 DSH 启动方式。若改为运行完整 DSH，则采用官方 CLI + profile/SDK 路线，不依赖已被移除的私有启动入口。

插件宿主按可信度或工作区分组；涉及会话状态的插件必须绑定会话作用域。退出、崩溃、重新加载要释放订阅、计时器、文件句柄和后台操作。独立进程只能改善故障隔离，并不自动限制文件、网络或系统命令访问。

### 5.2 第一批模块

建议新增独立模块承担：插件清单/版本与安装记录、运行宿主、DSH 兼容桥、统一工具注册和调度。`main.mjs` 只做装配，避免继续把所有插件功能加入主入口。

先将现有外部工具、浏览器和会话检索接入统一的工具入口，验证原有行为后再逐步迁移搜索等独立能力。任务循环、历史和记忆等核心能力放到后续，不让支持少量插件变成必须完成的大重写。

### 5.3 工具与权限

工具注册时必须记录归属、版本、参数约束、读写/联网/执行行为和可用范围。由宿主生成唯一工具名；禁止冒充内置工具、覆盖保留名称或撞名覆盖其他插件。

上游工具运行类本身依赖 `systemPrompt`，并要求输出声明、规范化返回值和结果渲染；不能把 `ctx.tools` 当成零依赖注册表。可行性验证必须确认这些契约及依赖能被有限兼容桥覆盖，覆盖不了就缩小支持清单或调整路线。

工具调用继续经过 DYWorker 的规则、确认、审计和结果处理。参数判断必须包含工作区外路径、目标地址、外发数据和命令；插件自称“只读”不能作为唯一授权依据。插件也可能在加载时、后台计时器或内部调用时产生副作用，不能只保护模型调用入口。

**已验证的接入风险：** 当前 `classify('dsh__sample__write')` 返回只读，`evaluateApproval` 在交互和只读模式均放行；相同测试名称换成现有 `mcp__` 前缀后，分别要求确认和拒绝。该测试只查询决策，没有执行写操作，说明的是未来直接注册新名称的风险，不是已经发生插件越权。

因此先补全未知外部工具的保守默认行为，再启用插件。后续使用显式注册的权限元数据；只给名称加前缀不能替代权限设计。

对于任意第三方 Node 插件，普通子进程无法保证原有文件和联网限制。第一期只开放经过审阅的可信插件；面向不可信市场插件前，需要验证各操作系统的真实隔离能力。不能向用户宣称安装确认后所有内部行为都会受逐次确认保护。

### 5.4 配置、安装与更新

- 插件目录放在应用数据目录，程序包保持只读；不得直接共用用户已有 DSH 的可执行包、锁文件和启用状态。
- 识别支持范围内的 DSH bundle/patch；涉及替换核心服务、访问绝对路径或未知依赖时拒绝该组合并说明原因。不能默默忽略不支持的配置。
- 安装先进入暂存区，检查包来源、锁定版本、依赖、许可证及安装脚本。默认禁止自动运行安装脚本；确需编译的插件逐个验证。
- 密钥通过现有安全存储按需提供，不把整套设置或主进程环境变量传入插件，也不写入普通配置或日志。
- 更新先验证再切换，保留上一个版本及对应配置。活动任务固定使用启动时的插件集合，停用先拒绝新调用，再等待或取消在途调用；第一期采用任务结束后生效，不承诺任意时刻热替换。
- 配置可以先行升级，但数据迁移须另有备份与兼容判断。恢复插件旧版本不等于能恢复被新插件改写的数据。

### 5.5 用户可见功能

第一期插件页提供：安装、启用/停用、配置、查看错误、移除和恢复上一版本。每个插件清楚显示是否通过本版本验证，以及需要访问什么。普通用户不需要直接编辑 Cordis 配置。

## 6. 阶段门槛

以下是根据现有项目结构给出的工程估算，不是已验证工期。按一名熟悉项目的开发人员估算；跨平台验收需对应设备。

| 阶段 |  | 交付与进入下一阶段的条件 |
|---|---:|---|
| 可行性验证 | 固定上游基线，选 2–3 个真实插件，至少一个工具类原样运行；确认依赖范围，跑通调用、拒绝、取消和卸载；失败则调整路线 |
| 基础接入与权限 | 独立宿主、有限兼容桥、统一工具入口、身份和权限、四类任务入口接通；原有相关行为回归通过 |
| 可用的插件管理 | 安装/停用/配置/恢复、清晰错误提示、受支持清单、依赖检查和凭据边界 |
| 打包与试用验收 | 在目标 macOS、Windows、Linux ARM64 环境验证安装、运行、断网、重启和清理；发布范围以实测平台为准 |

投入前的价值判断：若只有一两个能力需求，且已有现成的外部工具服务可实现，应比较直接接入成本；若计划持续维护多个扩展并利用 DSH 生态，建立 Cordis 扩展层的长期收益更明确。

## 7. 可行性验证和交付验收清单

试点样本应覆盖：一个无界面、低依赖的真实工具插件；一个带网络或文件访问的真实插件；一个依赖会话事件的插件，用来验证明确拒绝或识别依赖边界。另用自建最小插件覆盖崩溃、泄漏、重复名称等故障。没有目标插件清单前，不把示例插件通过等同于生态兼容。

1. 原样安装所选插件，完成真实工具注册、参数校验、返回文本/图片/错误的展示；记录是否修改过插件。
2. 拒绝授权后没有副作用；只读模式拒绝未知写入；内部调用、后台行为和启动阶段是否可能绕过限制都有明确结论。
3. 取消能到达执行端。超过宽限期无法停止时，结束对应宿主并明确影响范围；不能仅关闭等待就显示“已经停止”。
4. 停用后工具不再出现，事件和后台任务不残留；重复启停不重复注册；移除依赖后依赖它的插件有明确状态。
5. 不同会话、工作区及桌面/QQ/微信/定时/唤醒任务不串用凭据、历史、授权或插件状态。
6. 升级失败可恢复到已验证版本；断网重启能使用已安装且不依赖联网的插件；安装过程失败不破坏当前可用版本。
7. 原有办公文件、模型配置、浏览器、电脑操作、历史续跑、技能、确认和渠道收发不退化。需要真实服务或目标设备的验证单独记录，不用模拟测试代替。
8. 插件崩溃不拖垮主界面；敏感配置不出现在日志中；安装包和运行环境在每个对外承诺的平台验证通过。

## 8. 本次实际验证与结论边界

- 已检查现有依赖、工具执行入口、四类任务装配、技能发现、权限规则和桌面隔离配置。
- 运行现有针对外部工具的 6 项测试，**6 项通过、0 失败**：浏览器工具路由与确认；MCP 初始化/发现/调用；特定调用超时配置；单次取消保留共享连接；初始化超时关闭进程；外部工具进入用户确认流程。
- 运行上述未知工具名称的决策探针，复现需要先修补的接入风险。
- 测试使用模拟服务，不调用真实模型或 DSH 插件。不代表全项目回归、DSH 插件兼容或目标设备验证通过。
- 本次只新增评估资料；没有安装依赖、运行第三方插件、迁移历史或更改应用行为。

建议立项范围写为：**“引入 Cordis 扩展管理，首批支持明确清单内的 DSH 工具插件，并保留现有办公体验。”** 在真实插件验证之前，不写“全面兼容 DSH 插件”。
