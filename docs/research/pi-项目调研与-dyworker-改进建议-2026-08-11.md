# Pi 项目调研与 DYWorker 改进建议

调研日期：2026-08-11  
范围：仅评估 `earendil-works/pi` 的公开源码与官方文档，并对照当前 DYWorker 工作区；本报告不包含代码改动建议的直接实施。

## 结论先行

Pi 值得借鉴的不是它的终端界面，而是把“模型接入、任务过程、扩展、质量验证”做成清晰边界的方式。DYWorker 在本机办公、中文政务能力、消息渠道、风险确认和桌面适配上已经更适合目标用户；最应补的是任务可回溯性、稳定扩展边界、质量度量与发布供应链，而不是改成 Pi 的形态。

Pi 明确不内置对文件、进程、网络及凭据的限制，默认继承启动它的用户权限。因此不能复制其“扩展可直接运行”的默认模式；DYWorker 现有逐项确认、工作区外单次授权和审计记录必须保留并成为所有新增能力的前提。

## Pi 是什么

Pi 是 MIT 协议的本地开发者工具套件，包含统一模型访问、任务循环、终端交互、编码助手、会话存储、协议层和可选遥测组件。其核心不是单一应用，而是一组可独立使用的软件包：

| 组成 | Pi 的做法 | 对 DYWorker 的价值 |
| --- | --- | --- |
| 模型层 | 统一处理 OpenAI、Anthropic、Google 等接口，并允许每个模型声明上下文、推理、图片、费用与兼容差异 | 降低接入本地模型、内网模型和不同厂商时的临时适配风险 |
| 任务层 | 将模型调用、工具执行、状态保存与事件分开，支持顺序或并行的工具执行 | 更容易为定时任务、消息渠道与桌面任务保持一致行为 |
| 会话层 | 会话是带父子关系的记录树，可回到历史节点继续、分叉、复制，并可压缩旧上下文 | 适合“换一种方案试试”“从这里重新做”的真实工作流 |
| 扩展层 | 生命周期事件、工具、命令、界面与会话记录均有公开扩展入口 | 可把领域能力从主程序中拆开，减少每次新增能力都改核心流程 |
| 质量层 | 提供统一遥测约定、测试替身、评估包和本地发布冒烟检查 | 将“能跑”进一步变成“长期可观察、可复现地验证” |

Pi 官方仓库：<https://github.com/earendil-works/pi>；官方文档：<https://pi.dev/docs/latest>。

## 当前 DYWorker 已有优势

以下能力不是空白，后续改进应在其基础上完成：

1. **安全控制更适合产品使用。** DYWorker 已按操作风险、工作区内外位置、命令类型及审批模式决定是否确认，并记录操作、确认和结果。Pi 将这类安全责任交给容器或外部方案。
2. **本机事务能力更完整。** DYWorker 已覆盖文件、办公文档、网页、政府资料检索、敏感信息检查、本机应用操作、QQ/微信渠道、计划任务和恢复执行；Pi 的重点是开发工作流。
3. **面向中文办公的成品体验。** 公文检查、工作日计算、Word/Excel 输出、长期记忆和工作模板直接服务于非开发人员，Pi 没有对应的产品能力。
4. **已有多模型和上下文压缩基础。** 当前已经支持 OpenAI 兼容的两类接口、多个模型档案、图片转述、流式输出、用量记录、超限后的对话压缩，以及最多三个并行子任务。

## 需要改进的点（按优先级）

### P0：把任务记录升级为“可回到任意节点”的分支记录

**现状。** 当前任务以线性消息保存；虽然有任务历史搜索、恢复、上下文压缩和子任务，但用户不能从一条历史指令分出新路线，同时保留原路线可比较。

**建议。** 为每条任务消息保存稳定编号和父节点，提供三个明确动作：

- 从此处继续：回到任意历史节点并形成新分支；
- 复制当前路线：保留原任务不动，另开一条相同起点的路线；
- 对比路线：显示两条路线的目标、关键操作、文件变更和最终结论。

切换路线时，应让用户选择是否生成“离开路线摘要”；摘要、操作记录和确认记录都必须带上所属路线。

**原因。** 真实办公任务常在“保留原稿，再试一种写法”“两份数据口径并行核对”之间切换。Pi 的会话树已证明这是一种稳定的记录模型，可减少重复提问和误覆盖；DYWorker 的文件写入风险更高，因此对比与分支会比 Pi 更有价值。

**验收。** 在一个已有任务中回到任意用户消息，修改要求并继续；原路线仍完整可打开，两个分支的文件影响和审批记录可分别查看，恢复后不会把另一分支的上下文带入。

### P0：建立统一的任务事件和本地质量看板

**现状。** 当前有审计日志、调试日志和模型用量记录，但数据分散，难以回答“任务为什么慢、在哪一步失败、哪个工具最常失败、一次任务实际花费多少”。

**建议。** 定义一套只存本机的任务事件格式，覆盖：任务开始/结束、模型请求、工具调用、审批等待、子任务、重试、上下文压缩、失败原因和产出检查。为每个事件带任务、分支、渠道、模型和耗时等关联信息；默认不保存正文、附件内容、密钥和完整命令输出。随后在应用内提供按任务查看的时间线与汇总页。

**原因。** Pi 的遥测组件提供可替换、可测试的统一记录约定；借鉴这种边界，可以在不上传用户数据的前提下，定位卡顿、超时、重复确认和工具失败，避免靠零散日志排查。

**验收。** 能从一个任务页面看清每次等待发生在哪里；关闭该功能后不保留事件；导出的诊断包默认脱敏，且可由自动测试验证不含密钥和文件正文。

### P0：为核心任务建立可重复的“模拟模型”验收

**现状。** DYWorker 已有覆盖面较广的自动检查，但模型回答、工具调用序列、审批暂停/恢复、消息渠道与定时续跑的组合行为，仍缺少统一的可重复场景库。

**建议。** 增加不联网、不使用真实密钥的模拟模型，构建一组固定验收场景：

- 普通文件读取—生成—抽查；
- 高风险操作被拒绝、被批准、超时恢复；
- 工作区外单次授权不扩散；
- 三个子任务并行、其中一个失败；
- 上下文超限后的压缩与继续；
- 定时任务和 QQ/微信任务在无人值守时进入待确认状态；
- 模型服务返回异常格式、限流、断流、超时。

**原因。** Pi 将核心循环与测试替身、评估包分开，能够在不花模型费用的情况下反复验证行为。DYWorker 的渠道和审批更多，尤其需要防止一次改动破坏暂停、恢复和权限边界。

**验收。** 每个高风险或跨模块缺陷都有可重复的场景；发布前在无网络环境也能跑完，且失败报告能定位到场景和步骤。

### P1：把模型档案升级为“能力声明”，而不只是一组连接参数

**现状。** 现有档案已覆盖两类 OpenAI 兼容接口、密钥安全保存和视觉转述，但各家模型的真实能力、上下文大小、推理参数、图片直传、工具调用限制与费用规则没有统一对用户呈现。

**建议。** 每个模型档案增加能力卡：接口类型、文字/图片/文档输入、工具调用、推理档位、最大上下文、最大输出、费用或“未知”、兼容规则及最近一次连通性检查。新增适配时优先覆盖 Anthropic Messages 和 Google Generative AI；对内网兼容接口保留逐模型兼容开关，而不是假设所有 OpenAI 兼容服务行为一致。

**原因。** Pi 将这些差异放进模型声明，避免把厂商特例散落在任务循环中。对 DYWorker 而言，用户能在发起任务前知道“该模型能不能看图、适不适合长材料、能不能可靠调用工具”。

**验收。** 用户选择模型时能看见能力和限制；同一服务中的两个模型可有不同配置；连接检查不会暴露密钥；不支持的能力在任务开始前被明确提示。

### P1：提供受控的“领域扩展包”机制

**现状。** 当前已有工作模板、技能库、用户钩子和 MCP 工具，扩展能力已具雏形；但它们的版本、来源、权限范围、失败隔离和兼容性没有形成统一的产品规则。

**建议。** 建立扩展包清单：名称、版本、来源、作者、所需能力、适用工作区和启停状态。扩展只能通过受控接口注册工具、模板、渲染内容和任务事件；首次启用须逐项展示其需要访问的文件、网络、命令或外部服务。所有外部扩展仍走 DYWorker 的审批、审计和工作区范围控制，不能获得主进程的完全权限。

**原因。** Pi 的扩展体系证明生命周期与工具注册很有用，但其官方也明确提醒扩展拥有完整系统权限。DYWorker 可借鉴“公开入口”，不能借鉴“默认全权限”。

**验收。** 安装一个样例扩展后，可明确查看来源、版本和权限；禁用后不再出现在工具列表；扩展崩溃不会中断主任务；尝试访问工作区外或联网仍会触发原有确认。

### P1：从单体主流程逐步拆出稳定边界

**现状。** 任务循环、工具定义、风险判断、模型请求、压缩、子任务和多个桌面协调逻辑集中在少数大型文件中。功能很全，但变更时容易跨区域影响。

**建议。** 不做一次性重写，按新增需求逐步抽出四个边界：模型访问、任务记录与执行、工具及审批、桌面/渠道协调。先以现有行为测试为保护，再把重复的事件传递和状态处理迁移出去。

**原因。** Pi 的模块分层使命令行、程序接入和不同存储方式可以复用同一任务能力。DYWorker 不必变成通用开发工具，但需要让桌面、计划任务和消息渠道共用同一套可验证流程，减少分支行为不一致。

**验收。** 不改变用户看到的功能；同一任务从桌面、定时、QQ 或微信入口进入时，审批、审计、暂停与恢复结论一致；每次拆分都有原有场景回归通过。

### P2：加强发布依赖的可追溯与离线验收

**现状。** DYWorker 已有跨平台构建、标签校验和发布产物流程，但直接依赖大多允许自动取较新版本，发布前主要验证仓库内构建结果。

**建议。** 对直接依赖固定版本；增加依赖更新的最短观察期、定期安全检查、安装脚本白名单审查；发布前在仓库外的干净目录安装打包产物并完成启动、模型设置页、一次模拟任务和更新检查的基本验证。同时保留离线构建/验证说明与产物校验值。

**原因。** Pi 将依赖锁定、安装脚本控制、隔离安装冒烟测试和发布产物校验作为发布条件。DYWorker 要分发桌面安装包，本地仓库能构建并不足以证明用户安装后能正常启动。

**验收。** 任意发布候选版本都有独立安装验证记录和校验值；依赖变更可追溯；网络不可用时能明确区分“代码问题”和“下载问题”。

## 可借鉴但不宜直接照搬的点

| Pi 做法 | 为什么不能直接搬 | DYWorker 的正确做法 |
| --- | --- | --- |
| 扩展默认拥有本机全部权限 | 与办公文件、账号和本机控制场景不相容 | 扩展走受控接口，沿用逐项确认、范围限制和审计 |
| 通过容器或虚拟机解决安全 | 对普通桌面用户门槛高，且不覆盖所有本机办公能力 | 继续以内置风险分级为主；把隔离运行作为高风险开发任务的可选模式 |
| 终端优先交互 | 不适合 DYWorker 的非开发者目标用户 | 保留桌面操作和可视化进度，只吸收其任务状态模型 |
| 全量通用模型生态 | 会拉高维护成本，且不一定符合国内内网环境 | 先补最常见的两类接口和能力声明，再按用户需求扩展 |
| 公开会话分享 | 办公资料、政务材料和本机审计不适合默认分享 | 只提供用户主动导出的脱敏报告，默认绝不上传 |

## 建议实施顺序

1. **第一阶段（优先处理）：** 任务分支记录、统一本地任务事件、模拟模型场景库。它们能立刻提高可追溯性和改动安全性，且不改变外部产品边界。
2. **第二阶段：** 模型能力卡和受控扩展包。先做只读展示与权限清单，再逐步开放扩展入口。
3. **第三阶段：** 渐进拆分核心流程、隔离安装验证与供应链规则。每一步必须由第一阶段的场景库守住行为。

## 调研边界

本次未安装、运行或把 Pi 的代码接入 DYWorker；结论来自 Pi 官方源码与文档，以及对当前 DYWorker 源码和自动检查的静态核对。涉及真实模型效果、三方扩展稳定性和目标平台安装体验的建议，在实施前仍应做固定版本的隔离试验。
