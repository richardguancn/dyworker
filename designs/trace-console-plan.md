# 轨迹控制台改造计划（对照 DeepSeek Harness Trajectory）

状态：草案（待确认后实施）
日期：2026-08-14
范围：仅 DYWorker 桌面端（electron/ 与 src/ 渲染端），不涉及其他项目
关联：与 `designs/process-chain-visualization-plan.md` 共用同一条底层事件流，本计划是底层，链路视图是上层投影

## 1. 结论

方向成立，值得做。但要分清「学什么」和「不学什么」：

- 学：Trajectory 的界面形态（总览时间条 + 明细列表 + 选中详情，类似浏览器 Network 面板）和数据纪律（一切模型看到的内容都进同一条 append-only 事件流）。
- 不学：dsh 的「一切皆插件」（Cordis、scope、事件域）是框架级架构，与本次控制台改造目标无关，照搬会带来远大于收益的重构风险。

核心判断：我们缺的不是再采集更多日志，而是统一事件模型、轮次/步骤层级、记录关联、时间总览和虚拟化渲染。

## 2. 两边对照

| 维度 | DeepSeek Harness Trajectory | DYWorker 现状控制台 |
| --- | --- | --- |
| 数据基础 | append-only 会话事件日志：连续序号、写入前冻结校验、可持久化、可回放 | 运行时 `debug-log` 四类事件，只存内存、只留最后 300 条、不落盘、清空即丢 |
| 层级 | Turn（粗分割线）> Step（行内标记）> 记录（User / Assistant / Tool / 嵌套子工具） | 扁平列表，没有轮次/步骤层级 |
| 关联 | 请求↔响应↔调用↔结果、父子代理都能关联 | 各条彼此独立，子代理只加 ↳ 前缀混排 |
| 详情 | 选中后打开局部检查器：token、耗时、输入、输出、计时（含 TTFT） | 展开 `<pre>` 看截断正文（12k 上限） |
| 总览 | 顶部 Overview 时间条：按真实起止投影每条记录、TTFT 与解码分段、滚轮缩放、拖选区间过滤、右键清除/平移、进行中不虚构时长 | 无 |
| 列表 | 虚拟化只挂载可见行、从尾部打开、向上翻页加载更早、上滚暂停跟随 | 全量渲染、每次新日志强制滚底，看旧记录会被打断 |
| 检索 | 搜索、折叠、请求汇总、按来源筛选 | 只有清空和关闭 |
| 一致性 | 「模型可见即已记录」，恢复/分叉/回放共用同一事件流 | 对话、计划、活动、文件变更分散在多份状态里，日志只是另一份 |

## 3. 已有的原料（不重复建设）

- 事件已经存在：`debug-log`（模型请求/响应、工具调用/结果）、`token-usage`、`activity` / `activity-update`（带 id、状态、详情）、`plan-update`、`file-change`（带 +N/-M/diff）、`approval-request`、`ask-user`。
- 轮次已存在：模型请求日志里已有「第 N 轮」。
- `designs/process-chain-visualization-plan.md` 已定义 plan / activity / changes 的挂接方式，可复用。

所以这一期的工作不是加采集，而是：归一事件、补层级与关联、补计时、落盘、换渲染。

## 4. 改造方案（分阶段）

### Phase 1 统一事件流（electron/agent.mjs + src/types.ts）

1. 新增统一 `TraceEvent`：`seq`、`time`、`turn`、`step`、`kind`、`parentSeq`、`direction`（in/out）、`target`（模型/工具/系统）、`title`、`content`、`timing`（开始/首 token/结束）、`usage`。
2. 原四类 `debug-log` 映射进新 `kind`；`token-usage` 并入对应 `model-response` 记录；`tool-call` 与 `tool-result` 用 `parentSeq` 关联；子代理记录带 `parentSeq` 与 `depth`，渲染成嵌套分支。
3. 打点补 `turn` / `step`：用现有轮次 + 每次模型请求作为 step；在 `emit` 处统一追加 trace（保留现有 `debug-log` / `activity` 事件不动，保证向后兼容）。
4. 落盘：会话级 append-only 文件（或并入 `sessions.json` 的 trace 字段），异步写入不阻塞执行；内存只保留当前窗口。
5. `tests/agent.test.mjs` 补事件形状回归：序号、父子关联、计时、轮次/步骤、旧路径不受影响。

### Phase 2 控制台界面（src 渲染端 + styles.css）

1. 三区布局：顶部 Overview 时间条 / 中部明细列表 / 选中后的检查器。
2. 明细列表：Turn 粗分割、Step 行内标记、父子嵌套缩进、虚拟化 + 向上翻页 + 滚动暂停跟随。
3. 检查器：token、耗时、输入、输出、计时（含 TTFT）。
4. 交互：时间域缩放、拖选区间过滤、右键清除/平移、搜索、按类型/来源筛选、折叠、请求汇总；点击记录定位到对应消息或文件差异。

### Phase 3 与链路视图打通

- 上一份「需求→实现链路」计划改为从同一事件流投影：轨迹控制台是底层完整记录，聊天内的链路时间线是高层摘要，共享状态与配色。

### Phase 4 验证与收口

- 固定样本快照测试（渲染逻辑）+ agent 事件形状单测 + 真实会话端到端走查 + `npm run verify` 全绿。
- 老会话降级：无事件流时显示现有四类日志，或明确提示「该会话没有过程记录」。
- README 能力说明与截图；平台验证边界：macOS 本地验证，Windows / Linux 标注未验证。

## 5. 风险与取舍

- 不搬插件架构：只取「append-only 事件流 + 多投影」这一条，不动运行时结构。
- 落盘体量：大内容继续截断（维持 12k），每会话设条数上限，更早历史分页读取。
- 兼容：所有新字段可选；替换旧控制台前保留「简化视图」开关或先并行一段。
- 性能：虚拟化窗口、暂停跟随、区间过滤在前端完成，不额外请求主进程。
- 与现有未提交改动共存：窄改，Phase 0 先锁定基线。

## 6. 验收清单（DoD）

- 一条真实会话完整覆盖：用户消息 → 模型请求（含 token/耗时）→ 工具调用 → 结果 → 多轮 → 子代理分支 → 交付，全部可在轨迹视图按 Turn/Step 追溯；
- Overview 时间条与列表、检查器三者联动；缩放、区间过滤、搜索、折叠可用；
- 向上滚动加载更早历史且不打断阅读；进行中的记录不显示虚构耗时；
- 历史会话可回放（事件落盘），老会话优雅降级；
- `npm run verify` 全绿；快照测试与事件形状单测通过。
